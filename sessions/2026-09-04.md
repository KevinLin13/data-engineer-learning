## Correctly Reinforced Concepts

### `PARTITION BY` does not collapse rows

For:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY amount DESC
)
```

the input and output remain at order grain.

`PARTITION BY customer_id` creates independent calculation groups. It does not behave like `GROUP BY`.

Each customer therefore starts its Window Function calculation independently.

### Window Function vs `GROUP BY`

This query:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
)
```

preserves each order row and attaches the customer total to every row.

In contrast:

```sql
SELECT customer_id, SUM(amount)
FROM orders
GROUP BY customer_id;
```

collapses multiple order rows into one row per customer and therefore changes the grain.

### Ranking Functions

For values:

```text
500
500
300
```

results are:

```text
ROW_NUMBER(): 1, 2, 3
RANK():       1, 1, 3
DENSE_RANK():1, 1, 2
```

Key distinctions:

- `ROW_NUMBER()` always assigns a unique sequence number.
- `RANK()` gives ties the same rank and leaves gaps.
- `DENSE_RANK()` gives ties the same rank without gaps.

### Top-N per group

To select one highest-value order per customer:

```sql
ROW_NUMBER() OVER (
    PARTITION BY customer_id
    ORDER BY amount DESC
)
```

then filter:

```sql
WHERE rn = 1
```

If tied top values should all be retained, `RANK()` is more appropriate.

### Deterministic ranking

With:

```sql
ORDER BY amount DESC
```

two rows with identical `amount` do not have a guaranteed relative order.

When deterministic output is required:

```sql
ORDER BY amount DESC, order_id ASC
```

should be used.

### `LAG()` and `LEAD()`

`LAG(amount)` returns the previous row's value according to the Window Function ordering.

Example:

```text
amount | LAG(amount)
100    | NULL
300    | 100
250    | 300
```

`LEAD(amount)` returns the following row:

```text
amount | LEAD(amount)
100    | 300
300    | 250
250    | NULL
```

This supports calculations such as:

```sql
amount - LAG(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_date, order_id
)
```

to compare a row with the previous order.

# Round 1 Mistakes

## 1. Running Total

Incorrect mental model:

A Window `SUM()` with `ORDER BY` was initially interpreted as showing the complete partition total on every row.

Example:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_id
)
```

For:

```text
100
200
50
```

the expected cumulative result is:

```text
100
300
350
```

rather than:

```text
350
350
350
```

Correct distinction:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
)
```

produces the full customer total on each row.

Adding an appropriate ordering/frame makes it a running calculation.

Status after Round 2: **Improved**

---

## 2. Running Total vs `GROUP BY`

The following was incorrectly selected for cumulative customer spending:

```sql
SUM(amount)
GROUP BY customer_id
```

This produces the final total per customer and changes the output to customer grain.

A running total instead requires a Window Function such as:

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

This preserves order-level rows while calculating cumulative values.

Status after Round 2: **Improved**

---

## 3. Window Frame / peer rows

An important PostgreSQL behavior was introduced.

Given:

```text
order_id | order_date | amount
101      | 2026-09-01 | 100
102      | 2026-09-01 | 200
103      | 2026-09-02 | 50
```

and:

```sql
SUM(amount) OVER (
    ORDER BY order_date
)
```

the two rows with the same `order_date` are peers.

Under PostgreSQL's default Window Frame behavior, the result can be:

```text
300
300
350
```

rather than strict row-by-row:

```text
100
300
350
```

For explicit row-by-row accumulation:

```sql
SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

should be used.

Status after Round 2: **Improved**

---

## 4. Watermark advancement and failure recovery

Incorrect answer was given to the scenario:

```text
1. Fetch new data
2. Advance watermark
3. Write target
```

If target writing fails after the watermark has already advanced, the next run may skip those records entirely.

Correct safe ordering:

```text
Fetch
↓
Write target successfully
↓
Advance watermark
```

A stronger design is:

```text
BEGIN
↓
Write target
↓
Update watermark
↓
COMMIT
```

If any operation fails:

```text
ROLLBACK
```

This prevents the target state and checkpoint state from diverging.

Status: **Needs continued reinforcement**

# PostgreSQL Index Learning

## Composite index order

For:

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);
```

a strong matching pattern is:

```sql
WHERE customer_id = 'A'
  AND order_date >= '2026-09-01'
```

This follows the common pattern:

```text
leading column equality
+
following column range
```

Using only:

```sql
WHERE order_date >= ...
```

does not generally exploit the index as effectively because the leading `customer_id` is unconstrained.

However, this does **not** mean PostgreSQL can never use the index. Planner decisions remain cost-based.

---

## Range condition on leading index column

For:

```sql
WHERE customer_id > 'A'
  AND order_date >= '2026-09-01'
```

the first indexed column is already being scanned as a range.

Therefore the second indexed column generally cannot narrow the index search as effectively as in:

```sql
customer_id = 'A'
AND order_date >= ...
```

---

## Indexes can help ordering

With:

```sql
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, order_date);
```

a query such as:

```sql
WHERE customer_id = 'A'
ORDER BY order_date
```

may use the index both for filtering and for obtaining rows in the desired order.

PostgreSQL B-tree indexes can also normally be scanned backward, so:

```sql
ORDER BY order_date DESC
```

does not automatically require a separate descending index.

# `EXPLAIN` and `EXPLAIN ANALYZE`

Correct distinction:

```sql
EXPLAIN ...
```

shows the planner's estimated execution plan without executing a normal `SELECT`.

```sql
EXPLAIN ANALYZE ...
```

actually executes the query and reports real execution information.

Example:

```text
(cost=0.42..12.50 rows=100 ...)
(actual time=0.03..0.08 rows=50 ...)
```

means:

```text
Estimated rows = 100
Actual rows    = 50
```

`cost` is not elapsed seconds.

`actual time` contains actual runtime measurements.

Important operational note:

Using `EXPLAIN ANALYZE` on statements such as:

```sql
UPDATE
DELETE
INSERT
```

actually executes those changes unless they are protected by an explicit transaction and rolled back.

---

# Planner Estimates

A case such as:

```text
estimated rows = 100
actual rows    = 100000
```

means PostgreSQL severely underestimated cardinality.

This can cause the planner to choose an execution strategy based on an inaccurate expected workload.

Potential investigation areas discussed:

- stale statistics
- skewed data distributions
- relationships between columns not sufficiently represented by statistics

If a table has changed substantially, this may help:

```sql
ANALYZE orders;
```

`ANALYZE` refreshes planner statistics.

# Round 2 Mistake

## Selectivity and index usefulness

Incorrect answer implied that selectivity was irrelevant to index usefulness.

Correct concept:

```text
Having an index
≠
PostgreSQL must use the index
```

Suppose:

```text
orders rows = 1,000,000
customer_id = 'A' → 700,000 rows
customer_id = 'Z' → 50 rows
```

The query for `Z` is highly selective and is generally much more likely to benefit from an index.

The query for `A` returns most of the table, so PostgreSQL may reasonably prefer a sequential scan.

An index scan may require:

```text
index traversal
→ locate many tuple references
→ fetch many table pages
```

When most rows are needed, simply reading the table sequentially can be cheaper.

# Incremental Load

## Late-arriving data

Suppose:

```text
last_watermark = 10:00
```

and a record has:

```text
updated_at = 09:58
```

but does not become visible through the API until 10:05.

With:

```sql
WHERE updated_at > last_watermark
```

the row may never be captured.

The pipeline filters using the record's `updated_at`, not the time at which the API finally exposes it.

---

## Lookback Window

A mitigation is:

```text
effective_start =
last_watermark - lookback_window
```

then re-read a small overlapping period.

Because overlap deliberately causes duplicate extraction, it should be paired with:

```text
business key
+
UPSERT / deduplication
```

This trades a controlled amount of duplicate processing for lower late-arrival loss risk.

# Round 3 Mistake

## Crash after target write but before watermark update

Scenario:

```text
1. target write succeeds
2. watermark has not yet advanced
3. process crashes
```

The incorrect answer expected the watermark to advance automatically.

Correct behavior:

The watermark is still old.

Therefore the next run can fetch the same batch again.

The primary risk is:

```text
duplicate/repeated processing
```

rather than data loss.

This is why idempotent writes are important:

```text
business key
+
UNIQUE constraint
+
UPSERT / ON CONFLICT
```

The opposite failure order is more dangerous:

```text
watermark advances
↓
target write fails
```

because that can cause permanent data loss.

A useful mental model is therefore:

| Failure point | Main risk |
|---|---|
| target succeeds, watermark fails | duplicate processing |
| watermark succeeds, target fails | missed/lost data |

# Delete Handling

A watermark based only on:

```sql
WHERE updated_at > last_watermark
```

cannot necessarily detect hard deletes.

Suppose:

```text
Source before:
id = 123

Source after:
id = 123 no longer exists
```

If the source provides no delete record, the target receives no event indicating that deletion occurred.

Result:

```text
Source: id 123 absent
Target: id 123 still present
```

Possible solutions discussed:

- CDC
- soft delete
- tombstone / delete event
- periodic full reconciliation
- Snapshot Diff

# Soft Delete

With:

```text
id = 123
is_deleted = true
updated_at = 10:20
```

the delete becomes an observable update.

The incremental pipeline can therefore ingest the change and either:

- physically delete the target row
- or preserve the row while setting `is_deleted = true`

Soft delete therefore converts an otherwise invisible hard deletion into a normal incremental change event.

---

# CDC

CDC stands for **Change Data Capture**.

Its core purpose is to capture source changes such as:

```text
INSERT
UPDATE
DELETE
```

and make those changes available for incremental downstream processing.

Important distinction:

```text
Watermark ≠ CDC
```

A watermark is one strategy for discovering new or changed rows.

CDC is focused more directly on capturing the changes themselves, including deletes when the source technology supports them.

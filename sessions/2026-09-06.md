# Window Frame / Peer Rows

這是前一個 session 最主要的不穩定主題，本次進行了多次 delayed review。

核心資料：

```text
order_id | order_date | amount
---------|------------|-------
101      | 2026-09-01 | 100
102      | 2026-09-01 | 200
103      | 2026-09-02 | 50
```

若寫：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)
```

前兩列具有相同 `order_date`，形成 peer rows。

因此可能得到：

```text
300
300
350
```

而不是：

```text
100
300
350
```

## 嚴格逐 Row Running Total

需求若是：

```text
100
300
350
```

較穩定的寫法是：

```sql
SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

本次已能穩定區分兩個概念：

```text
ROWS
→ 定義 frame 以 physical rows 為單位

Deterministic ORDER BY
→ 定義同值 rows 之間的唯一順序
```

單獨使用 `ROWS` 並不代表 ties 的順序已被決定。

# Snapshot Diff

本次成功穩定區分四種情況。

## Inserted

```text
A 無
B 有
```

## Disappeared

```text
A 有
B 無
```

## Changed

```text
A 有
B 有
Business Key 相同
但被比較的業務欄位不同
```

## Duplicate

```text
同一 dataset / snapshot 中
同一 business key 非預期地出現多次
```

本次已不再把：

```text
same business key + different value
```

誤判為：

```text
Duplicate
```

而能穩定判定為：

```text
Changed
```

## Business Fields vs Technical Metadata

新加入的重要概念：

Snapshot Diff 不應無條件比較所有欄位。

例如：

```text
price
volume
status
```

可能屬於 business-relevant fields。

而：

```text
loaded_at
source_snapshot_id
processing_time
```

可能只是 technical metadata。

若：

```text
price = 50 → 50
source_snapshot_id = snap_A → snap_B
```

而比較目的只是偵測業務資料改變，則應是：

```text
Unchanged
```

若把每次 pipeline run 都會改變的 technical metadata 納入比較，會造成大量：

```text
False-positive Changed
```

# Incremental Load / Watermark / Checkpoint

這是本次題量最高的主題之一。

## Failure Order

### Target 成功，Watermark 失敗

```text
Target write success
↓
Watermark update fails
↓
Crash
```

主要風險：

```text
Replay / duplicate processing
```

因為 checkpoint 還在舊位置。

若 target 具備：

```text
Business Key
+ UNIQUE
+ UPSERT
```

重跑通常可以安全處理。

### Watermark 成功，Target 失敗

```text
Watermark advance
↓
Target write fails
↓
Crash
```

主要風險：

```text
Missed / lost data
```

因為下次執行可能從新的 checkpoint 後方開始。

## Transaction Boundary

若 target 與 watermark 都在同一 PostgreSQL database：

```sql
BEGIN;

UPSERT target;

UPDATE watermark;

COMMIT;
```

中途失敗：

```sql
ROLLBACK;
```

核心目標：

```text
Target State
+
Checkpoint State
=
Atomic State Transition
```

# Composite Checkpoint

只記：

```text
updated_at
```

可能遇到：

```text
多筆資料具有相同 timestamp
```

例如：

```text
id | updated_at
---|-----------
1  | 10:00:00
2  | 10:00:00
3  | 10:00:00
```

較精確的 checkpoint 可以使用：

```text
(updated_at, id)
```

例如上一輪處理到：

```text
(10:00:00, 2)
```

下一輪可以查：

```sql
WHERE updated_at > last_updated_at
   OR (
       updated_at = last_updated_at
       AND id > last_id
   )
ORDER BY updated_at, id;
```

概念上等同：

```text
(updated_at, id)
>
(last_updated_at, last_id)
```

## Tie-breaker

第二排序欄位 `id`：

```text
不必全域隨時間單調增加
```

重點是：

```text
對相同 updated_at
提供穩定且唯一的排序
```

# Late-arriving Data / Lookback Window

Composite checkpoint 能解決：

```text
相同 timestamp 的續跑邊界
```

但不能完全解決：

```text
late-arriving data
```

例如 checkpoint 已在：

```text
10:00
```

來源卻在稍後才補入：

```text
updated_at = 09:57
```

如果永遠只查：

```sql
WHERE updated_at > last_watermark
```

這筆資料可能永久遺漏。

因此可以使用：

```text
Lookback Window
```

例如每次從：

```text
last_watermark - 10 minutes
```

重新抓取。

由於這會刻意產生 overlap，因此必須搭配：

```text
Business Key
+ UNIQUE
+ Idempotent UPSERT
```

本次形成的整體 mental model：

```text
Composite Checkpoint
→ checkpoint precision

Lookback Window
→ late-arrival tolerance

Idempotent Write
→ replay safety
```

# Backfill

Backfill 與正常 incremental load 可能同時處理重疊區間。

例如：

```text
Backfill:
2026-08-01 ～ 2026-08-07

Scheduled Incremental:
2026-08-07
```

不需要假設：

```text
Backfill 開始
→ Incremental Load 一定自動停止
```

應依靠：

```text
Business Key
+ UNIQUE
+ UPSERT / Deduplication
```

讓相同資料可安全重跑。

# CDC / Delete Handling

## Hard Delete

來源直接：

```sql

WHERE id = 101;
```

```sql

```

row 已經不存在，所以可能完全無法知道：

```text

```

可考慮：

```text
CDC Delete Event
Tombstone
Soft Delete

```

## Soft Delete

例如：

```text
id = 101
is_deleted = true
updated_at = 11:05
```

row 仍存在，因此 incremental load 可以抓到刪除狀態。

# Python

## Mutable Default Argument

以下寫法：

```python
def add_item(item, items=[]):
    items.append(item)
    return items
```

預設 list 在函式定義時建立一次，因此會跨呼叫共用。

安全模式：

```python
def add_item(item, items=None):
    if items is None:
        items = []

    items.append(item)
    return items
```

本次 delayed review 再次答對。

若：

```python
record = {

}
```

以下：

```python
record.get("crop_name") is None
```

不能證明 key 不存在。

要確認 key existence：

```python

```

## Exception Handling

較好的錯誤處理：

```python
try:
    load_json(path)
except FileNotFoundError as e:
    raise RuntimeError(
        f"File not found: {path}"
    ) from e
```

重點：

```text
Catch specific exceptions
```

而不是：

```python

    pass
```

`raise ... from e` 可以保留 exception chain，方便 debugging。

# Schema Evolution

本次首次較集中練習。

## Additive Change

如果來源 API 新增：

```text
quality_grade
```

Raw layer 的合理方向是：

```text
先保留來源欄位
↓
評估 downstream schema / transform / validation
↓
決定是否納入 canonical model
```

不應因為來源多一個欄位就立即無條件丟棄整批資料。

## Breaking Change

原本：

```text
avg_price = 52.3
```

改為：

```text
avg_price = "52.3 元"
```

這可能是 breaking change。

需要檢查：

```text
Source schema / format
Transform
Type conversion
Validation
Downstream consumers
```

欄位名稱沒有改變，不代表 schema semantics 沒有改變。

# Profiling vs Validation

如果 canonical schema 明確要求：

```sql
avg_price DOUBLE PRECISION NOT NULL
```

資料出現：

```text
avg_price = NULL
```

就是明確 violation，應由 validation 攔下。

但若發現：

```text
lower_price = 0
volume > 0
```

而目前沒有 business rule 證明這種資料一定錯，則較合理的定位是：

```text
Profiling Finding / Anomaly
```

而不是直接：

```text
Invalid Data
```

核心原則：

```text
Observed anomaly
≠
proven data-quality failure
```

# Grain / Aggregation

假設 Silver：

```text
1 row
=
trade_date × crop_code × market_code
```

```sql
SELECT
    trade_date,
    market_code,
    AVG(avg_price)

    trade_date,
    market_code;
```

```text
1 row
=

```

```text
GROUP BY
```

## Multi-stage Aggregation

先建立：

```text

```

```sql
GROUP BY trade_date
```

```text
trade_date
```

本身完全可以合理。

```text
SUM 只能做一次
```

```text

→ Output Grain
```

# JOIN Fanout

假設：

```text
market_daily
grain = trade_date × market_code
```

而：

```text
market_tags
grain = market_code × tag
```

一個 market 有 3 個 tags。

直接 JOIN：

```sql
FROM market_daily m
JOIN market_tags t
    ON m.market_code = t.market_code
```

可能讓：

```text
market_volume = 100
```

展開成：

```text
100
100
100
```

再 `SUM()` 就得到錯誤的：

```text
300
```

## `EXISTS`

若目的只是：

```text
這個 market 是否具有某個 tag？
```

可以使用：

```sql
WHERE EXISTS (
    SELECT 1
    FROM market_tags t
    WHERE t.market_code = m.market_code
)
```

這通常只改變：

```text
row population
```

而不會把右表多筆 rows 展開到 output。

因此能避免不必要的 fanout。

# Final Micro-practical

資料：

```text
orders
grain = order
```

```text
order_items
grain = order × product
```

若：

```text
Order 1 → total = 100
Order 1 → 2 items

Order 2 → total = 200
Order 2 → 1 item
```

直接：

```sql
SELECT
    customer_id,
    SUM(order_total)
FROM orders
JOIN order_items
    USING (order_id)
GROUP BY customer_id;
```

JOIN 後：

```text
100
100
200
```

因此：

```text
SUM = 400
```

而真正 order-level total 是：

```text
300
```

此題成功辨識：

```text
1:N JOIN
→ Fanout
→ Measure duplication
→ Wrong aggregation
```

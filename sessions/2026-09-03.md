## Morning Session — Mistakes Worth Keeping

1. **JOIN output Grain** — A one-to-many join can move the result from customer grain to order
   grain; identify what one row represents after the join.
2. **`GROUP BY` and Grain** — `WHERE` filters rows, while `GROUP BY` aggregates and commonly
   changes the output grain to the grouping keys.
3. **Python Mutable Default Argument** — `items=[]` is created once at function definition;
   use `None` and initialize inside the function.
4. **`LEFT JOIN ... WHERE right_col IS NULL`** — this is a common Anti-Join pattern for finding
   left-side rows with no matching right-side row.
5. **`DISTINCT` and Grain** — determine the grain from the complete selected column combination,
   not from the presence of `DISTINCT` alone.
6. **Snapshot Diff: `Disappeared`** — a key present in Snapshot A but absent in Snapshot B is
   `Disappeared`.
7. **`dict.get()` vs key existence** — `record.get("volume") is None` cannot distinguish a
   missing key from `{"volume": None}`; use `"volume" in record`.

## Morning Session — New Learning

- Grain must be re-evaluated after `JOIN`, `GROUP BY`, and `DISTINCT`.
- Aggregating a measure at the wrong grain after a one-to-many join can create fanout and
  over-counting.
- `COUNT(*)` counts rows, while `COUNT(column)` excludes rows where that column is `NULL`.
- `NOT IN` can produce unexpected results when the subquery contains `NULL`; `NOT EXISTS` is a
  safer anti-join pattern in that situation.
- In a `LEFT JOIN`, conditions in `ON` preserve unmatched left rows; conditions in `WHERE` can
  remove them.
- PostgreSQL `CHECK` expressions that evaluate to `UNKNOWN` do not reject a row by themselves;
  combine `NOT NULL` with `CHECK` when the value is required.
- PostgreSQL allows multiple `NULL` values in a default `UNIQUE` column; add `NOT NULL` when the
  field is required.
- `ON CONFLICT` supports idempotent loading when combined with an appropriate business key or
  unique constraint.
- Canonicalization standardizes source field names and data types before downstream use.
- REST pagination uses `top` for page size and `skip` for the number of records to bypass.

## Afternoon Session — Mistakes Worth Keeping

1. **`dict.get()` versus key existence** — `record.get(key) is None` cannot distinguish a missing
   key from a present key with value `None`; use `key in record`.
2. **Window Function versus `GROUP BY`** — Window Functions normally preserve the input grain;
   `GROUP BY` is what aggregates rows into groups.
3. **Ranking functions** — `ROW_NUMBER()` gives every row a distinct sequence number, while
   `RANK()` and `DENSE_RANK()` assign equal ranks to ties; only `RANK()` leaves gaps.
4. **`PARTITION BY`** — it defines an independent calculation boundary, so ranking restarts in
   each partition; it does not collapse rows or create one global sequence.
5. **ACID Durability** — persistence after a successful `COMMIT` is Durability, not Consistency.

## Afternoon Session — New Learning

- A deterministic secondary sort such as `ORDER BY amount DESC, order_id ASC` is useful when
  `ROW_NUMBER()` must produce a stable result for tied values.
- A composite index such as `(customer_id, order_date)` is well aligned with equality filtering
  on `customer_id` followed by a range condition on `order_date`.
- Omitting the leading `customer_id` condition can limit how effectively that composite index is
  used for an `order_date`-only query.
- Normalization reduces insert, update, and delete anomalies caused by mixing entities at an
  inappropriate grain.
- Composite watermarks, lookback windows, deduplication, and UPSERTs work together to reduce
  missed records and duplicates in incremental pipelines.

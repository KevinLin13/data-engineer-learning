# Backfill

## 基本定義

假設正常 pipeline 每天只處理新增或更新的資料，但發現：

```text
2026-08-01 ～ 2026-08-07
```

因為程式 bug 沒有載入。

之後重新處理這段歷史資料，就是：

```text
Backfill
```

Backfill 的核心目的，是補齊過去原本應該存在但缺漏的資料。

## Backfill 與 Idempotency

Backfill 很容易遇到一個問題：

```text
無法完全確定某些歷史資料是否已經寫入 target
```

因此安全的設計是：

```text
Business Key
+
UNIQUE Constraint
+
UPSERT
```

這讓相同歷史區間可以安全重跑。

理想特性：

```text
Run once
≈
Run multiple times
```

也就是具備 idempotency。

## Backfill 與正常排程

Backfill 執行期間，正常 incremental load 可能仍持續執行。

例如：

```text
Backfill：
2026-08-01 ～ 2026-08-07

Scheduled Incremental Load：
2026-08-07
```

兩者可能處理重疊資料。

因此需要：

```text
Business Key
+
UNIQUE
+
UPSERT / Deduplication
```

Backfill 並不代表 incremental load 會自動停止。

# Incremental Load Failure Recovery

本輪已能正確區分兩種非常重要的 failure order。

## Case 1：Target 成功，但 Watermark 更新失敗

流程：

```text
last_watermark = 10:00

Fetch
↓
Target write success
↓
Watermark update fails
↓
Crash
```

此時 watermark 仍然是：

```text
10:00
```

所以下次執行可能再次抓取相同資料。

主要風險：

```text
Duplicate / Replay Processing
```

不是資料遺失。

如果 target 具備：

```text
Business Key
+
UNIQUE Constraint
+
UPSERT
```

則 replay 通常是安全的。

---

## Case 2：Watermark 成功，但 Target 寫入失敗

流程：

```text
Fetch
↓
Watermark → 11:00
↓
Target write fails
↓
Crash
```

下一次 pipeline 可能只抓：

```text
updated_at > 11:00
```

因此本次沒寫成功的資料可能永久不再被抓取。

主要風險：

```text
Missed / Lost Data
```

這比 duplicate processing 更危險。

## Failure Recovery Mental Model

| Failure State | Main Risk |
|---|---|
| Target success, Watermark failure | Replay / duplicate processing |
| Watermark success, Target failure | Missed / lost data |

這組概念本次已能正確回答。

# Transaction Boundary

如果 target table 與 watermark table 都位於同一個 PostgreSQL database，更安全的方式是：

```sql
BEGIN;

INSERT / UPSERT target;

UPDATE watermark;

COMMIT;
```

若中途失敗：

```sql
ROLLBACK;
```

目的不是單純要求：

```text
Target 一定先於 Watermark
```

而是更進一步讓：

```text
Target state
+
Checkpoint state
```

成為同一個 atomic transaction。

避免出現：

```text
target 寫入狀態
≠
watermark 狀態
```

# Delete Handling / CDC

## Hard Delete

如果來源資料：

```text
id = 101
```

被直接實體刪除：

```text
DELETE FROM source
WHERE id = 101;
```

而 pipeline 只執行：

```sql
WHERE updated_at > last_watermark
```

那麼被刪除的 row 已經不存在。

因此 incremental query 可能完全不知道：

```text
id = 101 已經消失
```

這也是 hard delete propagation 的困難。

## Soft Delete

若來源改成：

```text
id = 101
is_deleted = true
updated_at = 11:05
```

row 本身仍存在。

因此 incremental load 可以正常抓取：

```text
updated_at > last_watermark
```

並把刪除狀態同步到下游。

這是 soft delete 的重要優點。

## Tombstone / Delete Event

CDC 系統可能直接產生：

```text
id = 101
operation = DELETE
```

這就是：

```text
Tombstone / Delete Event
```

它明確告訴 downstream：

```text
這個 key 已經被刪除
```

因此下游可以：

```text
Hard delete target row
```

或：

```text
Mark target row as deleted
```

## Hard Delete 常見解法

若來源真的會 hard delete，可以考慮：

```text
CDC delete event
Tombstone
Soft delete
Periodic Snapshot Diff / Reconciliation
```

# Snapshot Diff

本輪再次練習 Snapshot A 與 Snapshot B 的方向。

## 核心分類

### Disappeared

```text
A 有
B 無
```

代表：

```text
Disappeared
```

### Inserted

```text
A 無
B 有
```

代表：

```text
Inserted
```

### Changed

```text
A 有
B 有
Business Key 相同
但欄位值改變
```

代表：

```text
Changed
```

例如：

```text
Snapshot A:
id = 101
price = 50

Snapshot B:
id = 101
price = 55
```

分類為：

```text
Changed
```

而不是 `Duplicate`。

# PostgreSQL Planner / Selectivity

假設：

```text
orders = 1,000,000 rows
```

且：

```sql
CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

查詢分布：

```text
customer_id = 'A'
→ 700,000 rows

customer_id = 'Z'
→ 50 rows
```

`Z` 的條件具有較高 selectivity。

因此：

```text
Z → 更可能 Index Scan
A → 可能 Seq Scan
```

核心概念：

```text
Having an index
≠
PostgreSQL must use the index
```

Planner 會依成本估算選擇執行策略。

```text
PostgreSQL 嚴重低估 cardinality
```

```text

```

```text

Skewed distribution
Column correlation
```


作用：

```text

提供 planner 更好的 cardinality estimate
```

# Window Frame / Peer Rows

這是本輪主要 SQL 錯誤。

資料：

```text
order_id | order_date | amount
101      | 2026-09-01 | 100
102      | 2026-09-01 | 200
103      | 2026-09-02 | 50
```

查詢：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)
```

本次錯誤預期為：

```text
100
300
350
```

但 PostgreSQL 預設 frame 對相同 `ORDER BY` 值具有 peer-aware 行為。

前兩筆：

```text
2026-09-01
2026-09-01
```

屬於 peers。

因此結果可以是：

```text
300
300
350
```

## 嚴格逐 Row Running Total

若需求是：

```text
第一列：100
第二列：300
第三列：350
```

則應明確寫：

```sql
SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

兩個關鍵：

```text
Deterministic ORDER BY
+
Explicit ROWS frame
```

# Python：`dict.get()` vs Key Existence

資料：

```python
record = {
    "crop_name": None
}
```

以下：

```python
record.get("crop_name") is None
```

結果為：

```python
True
```

但不能因此推論：

```text
crop_name key 不存在
```

因為兩種情況都可能回傳 `None`：

```python
{}
```

以及：

```python
{"crop_name": None}
```

因此判斷 key existence 應使用：

```python
"crop_name" in record
```

本次已正確回答。

這是前期 mistake log 中曾重複出現的錯誤，目前已成功 re-test。

# Python：Mutable Default Argument

程式：

```python
def add_item(x, items=[]):
    items.append(x)
    return items

print(add_item("A"))
print(add_item("B"))
```

結果：

```text
['A']
['A', 'B']
```

原因是：

```python
items=[]
```

這個預設 list 在函式定義時建立，之後沒有傳入 `items` 時會一直使用同一個物件。

不是每次 function call 都重新建立。

安全寫法：

```python
def add_item(x, items=None):
    if items is None:
        items = []

    items.append(x)
    return items
```

本次成功完成 delayed re-test。

## 2. PostgreSQL Window Frame / Peer Rows

### Incorrect Mental Model

對：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)
```

仍直接套用：

```text
strict row-by-row accumulation
```

### Correct Concept

如果 `ORDER BY` 欄位有 tied values：

```text
2026-09-01
2026-09-01
```

這些 rows 是 peers。

預設 Window Frame 可能使兩筆 peer rows 同時納入 frame。

因此：

```text
100, 200, 50
```

可以得到：

```text
300
300
350
```

而不是：

```text
100
300
350
```

嚴格逐列計算應使用：

```sql
ORDER BY order_date, order_id
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

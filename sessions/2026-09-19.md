# Window Frame / Peer Rows

這是本輪最重要的複習主題。

過去曾對：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)
```

誤判為一定會得到嚴格逐筆：

```text
100
300
350
```

但若：

```text
order_date
2026-09-01
2026-09-01
2026-09-02
```

前兩列具有相同 `ORDER BY` 值，因此它們是 peer rows。

PostgreSQL 預設 ordered window frame 可能得到：

```text
300
300
350
```

而不是：

```text
100
300
350
```

## 嚴格逐筆累積

若需求是：

```text
同一天也必須明確決定哪一筆先、哪一筆後
```

應使用：

```sql
SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

其中：

```sql
ORDER BY order_date, order_id
```

負責建立 deterministic ordering。

而：

```sql
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
```

表示：

```text
從 partition 第一列
一路累積到目前這一列
```

## `ROWS` vs `RANGE`

本輪已能正確區分：

```text
ROWS
→ 依實際 row position 決定 frame

RANGE
→ 依 ORDER BY value 決定 frame
→ 相同排序值可能形成 peer group
```

因此當排序欄位可能有 ties 時：

```sql
ORDER BY order_date
```

不能直接假設一定會逐列累積。

## 每位客戶各自累積

完整需求：

```text
每個 customer 各自重新開始
同一天依 order_id 排序
嚴格逐筆累積
```

正確寫法：

```sql
SUM(amount) OVER (
    PARTITION BY customer_id
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

可以拆成三件事：

```text
PARTITION BY customer_id
→ 每位客戶各算各的

ORDER BY order_date, order_id
→ 建立明確交易順序

ROWS ...
→ 逐列累積
```

# Schema Evolution / Migration

本輪 migration 基本流程維持穩定。

假設原本：

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    amount NUMERIC NOT NULL
);
```

現在要新增：

```sql
source_system TEXT NOT NULL
```

但舊版 application 尚未寫入此欄位。

安全流程為：

```text
1. 新增 nullable column
2. 部署新版 application
3. 開始寫入新欄位
4. Backfill 舊資料
5. 確認沒有 NULL
6. 最後加入 NOT NULL
```

例如：

```sql
ALTER TABLE orders
ADD COLUMN source_system TEXT;
```

而不是一開始就：

```sql
ALTER TABLE orders
ADD COLUMN source_system TEXT NOT NULL;
```

## Breaking Change

上游原本：

```json
{
  "average_price": 52.3
}
```

改成：

```json
{
  "average_price": "52.3 元"
}
```

即使欄位名稱沒變，仍可能是 breaking change。

因為既有程式：

```python
float(record["average_price"])
```

無法直接處理：

```python
float("52.3 元")
```

因此判斷 compatibility 不能只看：

```text
欄位名稱
```

還要看：

```text
型別
格式
nullable
semantic contract
```

# GitHub Actions / CI

本輪 CI 題型全部答對。

## 典型 CI Workflow

需求：

```text
push 到 main
或
開 Pull Request
```

時自動執行：

```bash
pytest
```

典型 workflow：

```yaml
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - run: pip install -r requirements.txt

      - run: pytest
```

核心流程：

```text
checkout
→ setup Python
→ install dependencies
→ run tests
```

## CI 環境

若本機：

```text
51 passed
```

但 CI 出現：

```text
ModuleNotFoundError: No module named 'pandas'
```

第一優先應檢查：

```text
CI 是否安裝 dependencies
requirements.txt 是否包含 pandas
使用的 Python environment 是否正確
```

因為 CI runner 可視為新的乾淨環境。

## Exit Code

若：

```text
48 passed
2 failed
```

pytest 通常會回傳：

```text
non-zero exit code
```

因此 GitHub Actions step 通常會失敗。

目前掌握：

```text
0
→ 通常成功

non-zero
→ 通常代表失敗／錯誤
```

即可。

# Data Modeling

本輪 Data Modeling 表現穩定。

## Grain

如果需求：

```text
一列 = 一個訂單中的一個商品
```

則 grain 是：

```text
order item
```

不能只看某一個欄位來判斷 grain，而要問：

```text
一列到底代表什麼？
```

## JOIN Fanout

`orders`：

```text
一列 = 一張訂單
```

`order_items`：

```text
一列 = 一張訂單中的一個商品
```

如果：

```sql
SELECT SUM(o.order_total)
FROM orders o
JOIN order_items i
    ON o.order_id = i.order_id;
```

一張訂單有 4 個 items：

```text
order_total = 1000
```

JOIN 後可能變成：

```text
1000
1000
1000
1000
```

再 SUM：

```text
4000
```

造成 measure 膨脹。

因此：

```text
聚合前先確認 JOIN 後的 grain
```

仍是核心原則。




```text

```

# Incremental Load

本輪持續穩定。

## Composite Checkpoint

若：

```text
last_updated_at = 2026-09-19 10:00:00
last_id = 120
```

而來源有：

```text
120 | 10:00:00
121 | 10:00:00
122 | 10:00:01
```

只使用：

```sql
WHERE updated_at > :last_updated_at
```

會漏掉：

```text
121 | 10:00:00
```

因此可使用：

```sql
WHERE updated_at > :last_updated_at
   OR (
       updated_at = :last_updated_at
       AND id > :last_id
   )
```

也就是：

```text
(updated_at, id)
```

作為 composite checkpoint。

## Late-arriving Data

如果來源會有 late-arriving data，可以使用：

```text
lookback window
+
idempotent upsert
```

例如每次不要只從：

```text
last_watermark
```

開始抓，而是：

```text
last_watermark - 1 day
```

重新抓一小段重疊區間。

因為會重新讀到舊資料，因此 target 寫入必須能安全 replay。

# Snapshot Diff

本輪延遲複習仍然答對。

以 Snapshot A → Snapshot B：

```text
A 有、B 沒有
→ Disappeared

A 沒有、B 有
→ Inserted

A、B 都有相同 key
但 business value 改變
→ Changed
```

需要注意：

```text
Same key
≠ Duplicate
```

`Duplicate` 通常指同一 dataset 內同 key 或同 row 重複出現。

```python
try:
    ...

```

# PostgreSQL Transaction

若 migration：

```sql
BEGIN;

ALTER TABLE orders
ADD COLUMN source_system TEXT;

UPDATE orders
SET source_system = 'legacy'
WHERE source_system IS NULL;

ALTER TABLE orders
ALTER COLUMN source_system SET NOT NULL;
```

最後一步失敗，而且尚未：

```sql
COMMIT;
```

則可：

```sql
ROLLBACK;
```

回復 transaction 內尚未提交的變更。

本輪已能正確掌握：

```text
BEGIN
→ 多步變更
→ 成功才 COMMIT
→ 失敗可 ROLLBACK
```

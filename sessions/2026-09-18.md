# Schema Evolution / Migration

本輪對 migration 的基本 rollout 流程已能穩定判斷。

## 新增 Required Column

原本：

```sql
CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    amount NUMERIC(10,2) NOT NULL
);

```

若要新增最終必須為：

```sql
source_system TEXT NOT NULL

```

但舊版 application 尚未寫入此欄位，安全流程是：

```text
1. 新增 nullable column
2. 部署新版 application，開始寫入
3. Backfill 舊資料
4. 確認沒有 NULL
5. 最後加入 NOT NULL

```

例如：

```sql
ALTER TABLE orders
ADD COLUMN source_system TEXT;

```

而不是一開始就直接：

```sql
ALTER TABLE orders
ADD COLUMN source_system TEXT NOT NULL;

```

## Backfill

即使新版 application 已經會寫入：

```text
source_system = 'api_v2'

```

既有 rows 仍可能保持：

```text
source_system = NULL

```

因此在：

```sql
ALTER TABLE orders
ALTER COLUMN source_system SET NOT NULL;

```

之前，必須先處理舊資料。

## Breaking Change

Upstream 原本：

```json
{
  "average_price": 52.3
}

```

後來改成：

```json
{
  "average_price": "52.3 元"
}

```

即使欄位名稱沒有變，仍可能是 breaking change。

因為既有：

```python
float(record["average_price"])

```

無法直接處理：

```python
float("52.3 元")

```

所以判斷 schema compatibility 不能只看欄位名稱，也要看：

- 型別
- 格式
- nullable 狀態
- semantic contract

# Raw Validation vs Transform

本輪再次確認兩層責任不同。

若 Raw Validation 只要求：

```text
欄位存在
JSON 結構正確

```

那：

```json
{
  "average_price": "abc"
}

```

仍可能通過 Raw Validation。

但後續：

```python
float("abc")

```

會失敗。

可整理成：

```text
Raw Validation
→ 來源 payload 是否具有預期結構

Transform / Canonicalization
→ 能否轉換成內部需要的標準資料型別

Data Quality
→ 是否符合明確資料／業務規則

```

# GitHub Actions / CI

本輪 CI 基礎概念全部答對。

## 典型 CI Flow

專案希望在：

```text
push
Pull Request

```

時自動執行：

```bash
pytest

```

典型設計為：

```text
.github/workflows/test.yml

```

概念流程：

```text
checkout repository
→ setup Python
→ install dependencies
→ pytest

```

## CI Failure

若結果：

```text
51 passed
1 failed

```

pytest 通常會回傳：

```text
non-zero exit code

```

因此 GitHub Actions step 通常會被判定為失敗。

目前只需要掌握：

```text
0
→ 通常代表成功

non-zero
→ 通常代表發生錯誤／失敗

```

不需要背所有 exit code 的個別數字含義。

## Dependency Problem

若：

```text
本機測試正常
CI: ModuleNotFoundError: No module named 'pandas'

```

第一優先應檢查：

```text
requirements.txt 是否包含 pandas
pip install 是否真的執行
CI 使用的 Python environment 是否正確

```

而不是直接認為 pandas 或 pytest 有問題。

# Bronze / Silver / Gold

本輪三層架構辨識穩定。

## Bronze

API 原始資料：

```json
{
  "交易日期": "2026/09/18",
  "平均價": "52.3",
  "市場名稱": "台北一"
}

```

若需求是：

```text
盡量保留來源原貌
方便追查 upstream
方便重新處理

```

適合放 Bronze。

## Silver

完成：

```text
欄位重新命名
日期標準化
型別轉換
dedup
基本 Data Quality

```

例如：

```text
trade_date   DATE
avg_price    NUMERIC
market_name  TEXT

```

較符合 Silver。

## Gold

若 BI Dashboard 只需要：

```text
每天 × 市場
總交易量
平均價格

```

就可以建立：

```sql
SELECT
    trade_date,
    market_code,
    SUM(volume) AS total_volume,
    AVG(avg_price) AS avg_price
FROM silver_table
GROUP BY
    trade_date,
    market_code;

```

輸出 grain：

```text
trade_date × market_code

```

屬於典型 Gold layer。

目前可快速記成：

```text
Bronze
→ 原始

Silver
→ 清理、標準化、可重用

Gold
→ 分析／報表需求導向

```

# Data Modeling / Grain / JOIN Fanout

本輪相關題目全部答對。

## JOIN Fanout

`orders`：

```text
一列 = 一張訂單

```

`order_items`：

```text
一列 = 一張訂單的一個品項

```

若：

```sql
SELECT SUM(o.order_total)
FROM orders o
JOIN order_items i
    ON o.order_id = i.order_id;

```

一張訂單有 3 個 items 時：

```text
100

```

可能 JOIN 成：

```text
100
100
100

```

再 SUM：

```text
300

```

造成 measure 膨脹。

核心觀念：

```text
聚合前一定先確認 JOIN 後的 grain。

```

## `EXISTS`

若需求只是：

```text
找出至少有一個 item 的訂單

```

較適合：

```sql
SELECT o.*
FROM orders o
WHERE EXISTS (
    SELECT 1
    FROM order_items i
    WHERE i.order_id = o.order_id
);

```

因為只做存在性判斷，不需要把 item rows 展開。

## Fact Table Grain

若需求明確定義：

```text
一列 = 一個訂單品項

```

則 fact table grain 就是：

```text
order item

```

通常可包含：

```text
order_id
product_id
quantity
unit_price
amount

```

應遵循：

```text
先定義 grain
→ 再決定 dimension keys
→ 再決定 measures

```

# Python

## Exception Handling

以下寫法：

```python
try:
    ...
except:
    return {}

```

問題是可能吞掉大量非預期錯誤。

可能形成：

```text
真正 bug
→ 被 except 吃掉
→ 回傳 {}
→ 下游才出現錯誤
→ debugging 更困難

```

較好的方向是捕捉具體 exception：

```python
except FileNotFoundError:
    ...
except json.JSONDecodeError:
    ...

```

## `json.load()`

```python
with open("data.json", "r", encoding="utf-8") as f:
    data = json.load(f)

```

其中：

```python
json.load(f)

```

表示：

```text
從已開啟的 file object
→ 讀取 JSON
→ 解析成 Python object

```

需要區分：

```python
json.load(f)

```

→ file object

```python
json.loads(text)

```

→ JSON string

## pytest Expected Exception

若：

```python
def divide(a, b):
    return a / b

```

要測：

```text
b = 0
→ ZeroDivisionError

```

可寫：

```python
with pytest.raises(ZeroDivisionError):
    divide(10, 0)

```

# Incremental Load Delayed Review

目前 checkpoint：

```text
last_watermark = 2026-09-18 10:00:00

```

查詢：

```sql
WHERE updated_at > :last_watermark

```

如果還有尚未處理完成的資料：

```text
updated_at = 2026-09-18 10:00:00

```

下一次 query 因為使用：

```text
>

```

這些 rows 不會再被選中，可能永久遺漏。

之前學過的解法是 composite checkpoint：

```text
(updated_at, id)

```

搭配：

```sql
WHERE updated_at > :last_updated_at
   OR (
       updated_at = :last_updated_at
       AND id > :last_id
   )

```

本次 delayed review 答對，概念維持穩定。

# Snapshot Diff Delayed Review

Business key：

```text
trade_date + crop_code + market_code

```

Snapshot A：

```text
2026-09-17 | A01 | M01 | 50

```

Snapshot B：

```text
2026-09-17 | A01 | M01 | 55

```

Business key 相同，但：

```text
avg_price
50 → 55

```

所以分類：

```text
Changed

```

應持續區分：

```text
A 無、B 有
→ Inserted

A 有、B 無
→ Disappeared

A、B key 相同，但業務值不同
→ Changed

同一 dataset 中相同 business key 多次出現
→ Duplicate

```

本次 delayed review 答對。

# Window Frame / Peer Rows

這是本次唯一錯題，也是過去已出現在 mistake log 的重複弱點。

資料：

```text
order_id | order_date | amount
101      | 2026-09-01 | 100
102      | 2026-09-01 | 200
103      | 2026-09-02 | 50

```

SQL：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)

```

本次誤答：

```text
100
300
350

```

正確應理解為 PostgreSQL 預設 ordered window frame 對相同 `ORDER BY` value 的 rows 有 peer-aware 行為，因此可得到：

```text
300
300
350

```

前兩筆：

```text
order_date = 2026-09-01

```

屬於 peer rows，因此第一個 ordering group 已包含兩筆：

```text
100 + 200 = 300

```

## 嚴格逐 Row Running Total

如果真正需求是：

```text
100
300
350

```

應明確使用：

```sql
SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)

```

必須分開理解：

```text
ROWS
→ frame 以 physical rows 為單位

ORDER BY order_date, order_id
→ 提供 deterministic row ordering

```

只有：

```sql
ROWS BETWEEN ...

```

仍不代表 tied rows 的先後順序已經被唯一決定。

# Mistake Analysis

## Window Frame / Peer Rows

### 本次錯誤

看到：

```sql
SUM(amount) OVER (
    ORDER BY order_date
)

```

仍直覺套用：

```text
第一 row = 100
第二 row = 100 + 200
第三 row = 100 + 200 + 50

```

也就是把 ordered Window `SUM()` 直接理解成「嚴格逐 row 累加」。

### Root Cause

尚未完全建立：

```text
ORDER BY
≠
一定逐 row running total

```

在 PostgreSQL 中：

```text
相同 ORDER BY 值
→ peer rows

```

預設 frame 行為可能把 peers 一起包含進當前 frame。

### Correct Mental Model

判斷 running total 時應先問：

```text
1. ORDER BY 是否有 ties？
2. Window frame 是什麼？
3. 是否需要 deterministic ordering？

```

如果需求明確是：

```text
逐筆、唯一順序累積

```

優先考慮：

```sql
ORDER BY unique_ordering_columns
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

```

### Status

建議 mistake log 狀態：

```text
Improved → Partial / Needs Review

```

原因：

此概念雖曾在 2026-09-06 多次 delayed review 答對，但 2026-09-18 再次答錯，代表仍未完全內化。
